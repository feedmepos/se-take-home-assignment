# McDonald's Order Controller — Design Spec

**Date:** 2026-07-29  
**Scope:** Go backend CLI only (interactive + demo mode)  
**Approach:** Controller + one goroutine per bot

## Goals

Build an in-memory order controller CLI that:

1. Accepts Normal and VIP orders into a PENDING area
2. Prioritizes VIP ahead of Normal (FIFO within each tier)
3. Supports adding/removing cooking bots; each bot processes one order at a time
4. Completes each order after a configurable processing duration (default 10s)
5. On bot removal mid-process, returns the order to PENDING with correct priority
6. Emits timestamped logs (`HH:MM:SS`) for CI via `scripts/result.txt`
7. Passes GitHub Actions `backend-verify-result` workflow

Out of scope: frontend UI, data persistence, network API.

## Architecture

```
cmd/order-controller/main.go   # flags, mode selection
internal/order/                # Order model & status
internal/bot/                  # Bot model & lifecycle helpers
internal/controller/           # Thread-safe queues, bot pool, dispatch
internal/cli/                  # Interactive REPL + demo scenario
scripts/{test,build,run}.sh
scripts/result.txt             # generated by run.sh
```

| Module | Responsibility |
|--------|----------------|
| `order` | Order struct, type (`NORMAL`/`VIP`), status (`PENDING`/`PROCESSING`/`COMPLETE`) |
| `bot` | Bot struct, status (`IDLE`/`PROCESSING`), cancel context |
| `controller` | PENDING/COMPLETE lists, VIP insert, bot pool, mutex-protected ops |
| `cli` | Command parsing, interactive loop, demo orchestration, logging |

## Data Model

### Order

- `ID` — unique, monotonically increasing from 1
- `Type` — `NORMAL` | `VIP`
- `Status` — `PENDING` | `PROCESSING` | `COMPLETE`

### Bot

- `ID` — unique, monotonically increasing from 1
- `Status` — `IDLE` | `PROCESSING`
- `CurrentOrder` — optional pointer to order being processed
- Cancel via `context.Context` for `-bot`

### PENDING queue rules

1. Normal order → append to tail
2. VIP order → insert after all existing VIP orders and before the first Normal order
3. Interrupted (requeued) orders use the same rules (priority by type, not original index)

Example: `[VIP#1, VIP#2, N#3, N#4]`

- New VIP → `[VIP#1, VIP#2, VIP#5, N#3, N#4]`
- New Normal → `[VIP#1, VIP#2, N#3, N#4, N#6]`

### COMPLETE

Append-only by completion time; not re-dispatched.

## Bot Lifecycle & Concurrency

### `+ Bot`

1. Create bot, append to pool (creation order preserved; `-bot` removes newest)
2. Start goroutine loop:
   - Dequeue head of PENDING → mark `PROCESSING`
   - If empty → mark `IDLE`, wait for new-order or destroy signal
   - If order assigned → `select` on `time.After(processTime)` (complete) or `ctx.Done()` (requeue)

### `- Bot`

1. Remove newest bot from pool and cancel its context
2. If processing: set order status back to `PENDING`, re-insert by VIP/Normal rules
3. Goroutine exits; bot destroyed

### Concurrency

- Single `sync.Mutex` on `OrderController` for queues and bot list
- State mutations only under lock; sleep/wait outside lock
- New orders wake idle bots via `sync.Cond` (`Broadcast` under the same mutex)
- Flag `-process-time` (default `10s`); demo/tests may use `100ms`

## CLI Interface

### Flags

- `-demo` — run non-interactive demo scenario, then exit
- `-process-time` — order processing duration (default `10s`)

### Interactive commands

| Command | Action |
|---------|--------|
| `n` / `new normal` | Create Normal order |
| `v` / `new vip` | Create VIP order |
| `+` / `+bot` | Add bot |
| `-` / `-bot` | Destroy newest bot |
| `s` / `status` | Print PENDING / PROCESSING / COMPLETE / bots |
| `q` / `quit` | Exit |

All significant events log with `[HH:MM:SS]` prefixes.

### Demo scenario (`-demo`)

Used by CI / `run.sh`:

1. Create Normal, VIP, Normal — assert VIP ordering in logs
2. `+bot` twice — parallel processing
3. Wait for completions; create another VIP — idle bot picks up immediately
4. `-bot` (including idle destroy case as needed)
5. Print final summary to stdout

## Scripts

- `scripts/test.sh` → `go test ./... -v`
- `scripts/build.sh` → `go build -o bin/order-controller ./cmd/order-controller`
- `scripts/run.sh` → `./bin/order-controller -demo -process-time=100ms > scripts/result.txt`

## Testing

Unit tests focus on:

1. VIP insert order relative to Normal
2. Unique increasing order IDs
3. `+bot` immediately picks PENDING
4. `-bot` mid-process requeues with correct priority
5. Multiple bots process in parallel
6. Idle bot wakes on new order

Use short `-process-time` (or inject duration into controller) in tests.

## Delivery

1. Implement on a feature branch
2. Open Pull Request to `main`
3. Ensure `backend-verify-result` GitHub Action passes (`result.txt` non-empty, contains `HH:MM:SS`)

## Decisions Log

| Decision | Choice |
|----------|--------|
| CLI mode | Both interactive and `-demo` |
| Process duration | Configurable via `-process-time` (default 10s) |
| Delivery scope | Go backend CLI only |
| Concurrency model | One goroutine per bot + mutex-protected controller |
