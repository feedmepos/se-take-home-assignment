# 设计文档

## 1. 技术栈

后端技术栈：

- Golang
- 标准库 `net/http`
- 内存业务状态管理
- `sync.RWMutex` 保证 Controller 线程安全
- 后台定时轮询协程推进订单状态

前端技术栈：

- Vue 3
- Vite
- 原生 CSS
- HTTP API 调用后端

部署方式：

- 本地：Docker Compose
- 服务器：Docker 容器 + 宿主机 nginx + HTTPS 证书

## 2. 总体架构

```text
Vue Frontend
    |
    | HTTP API
    v
Go Backend API
    |
    v
Controller
    |
    | sync.RWMutex
    v
In-memory business state
```

后端启动时初始化一个 Controller。Controller 是业务状态的唯一维护者，负责保存订单队列、bot 状态、完成订单和事件日志。

前端不维护业务规则，只负责调用后端 API 并展示后端返回的数据。

## 3. Controller 设计

Controller 位于 `internal/controller/controller.go`。

Controller 内部维护：

```go
type Controller struct {
    mu sync.RWMutex

    nextOrderID int
    nextBotID   int
    processTime time.Duration

    pending   []*Order
    completed []*Order
    bots      []*Bot
    events    []string
}
```

字段说明：

- `mu`：读写锁，保证 Controller 自身线程安全。
- `nextOrderID`：下一个订单号，默认从 `1001` 开始。
- `nextBotID`：下一个 bot 编号。
- `processTime`：订单处理耗时，默认 10 秒。
- `pending`：等待处理的订单队列。
- `completed`：已完成订单列表。
- `bots`：当前 bot 列表。
- `events`：活动日志。

订单模型：

```go
type Order struct {
    ID          int
    Kind        OrderKind
    Status      OrderStatus
    CreatedAt   time.Time
    StartedAt   time.Time
    CompletedAt time.Time
}
```

bot 模型：

```go
type Bot struct {
    ID         int
    Status     BotStatus
    Order      *Order
    StartedAt  time.Time
    CompleteAt time.Time
}
```

## 4. 线程安全设计

Controller 自己负责线程安全，而不是只依赖 API 层加锁。这样做的原因是：Controller 会被 HTTP API、后台 scheduler 和 CLI 复用，把锁放在 Controller 内部可以避免未来新增入口时绕过并发保护。

### 4.1 读锁

只读取状态时使用 `RLock`。

典型方法：

- `Snapshot()`
- `Events()`
- `WriteEvents()`

示例：

```go
func (c *Controller) Snapshot() Snapshot {
    c.mu.RLock()
    defer c.mu.RUnlock()

    // copy current state
}
```

### 4.2 写锁

会修改状态时使用 `Lock`。

典型方法：

- `Init()`
- `Reset()`
- `AddOrder()`
- `AddBot()`
- `RemoveNewestBot()`
- `AdvanceTo()`

示例：

```go
func (c *Controller) AddOrder(kind OrderKind, now time.Time) *Order {
    c.mu.Lock()
    defer c.mu.Unlock()

    // create order and dispatch idle bots
}
```

这样可以保证：

- 订单号不会并发重复。
- Pending 队列不会并发写坏。
- bot 不会重复接单。
- scheduler 推进状态时不会和 HTTP 请求互相覆盖。

## 5. 订单优先级设计

订单分为：

- `Normal`
- `VIP`

Pending 队列规则：

1. VIP 订单优先于 Normal 订单。
2. VIP 内部按订单号递增。
3. Normal 内部按订单号递增。

实现方式：

```go
sort.SliceStable(c.pending, func(i, j int) bool {
    left, right := c.pending[i], c.pending[j]
    if left.Kind != right.Kind {
        return left.Kind == VIP
    }
    return left.ID < right.ID
})
```

由于订单号递增，所以按订单号排序可以代表同类型订单的创建顺序。

## 6. Bot 调度设计

每个 bot 一次只能处理一个订单。

触发调度的场景：

- 创建订单后。
- 创建 bot 后。
- bot 完成订单后。
- 删除 bot 后订单回到 Pending 时。

调度流程：

```text
查找 IDLE bot
    |
    v
取 pending 队列中最高优先级订单
    |
    v
订单状态改为 PROCESSING
    |
    v
bot 状态改为 PROCESSING
    |
    v
设置 CompleteAt = now + 10s
```

当 bot 完成订单后：

```text
订单进入 completed
bot 变回 IDLE
继续尝试处理 pending 中下一单
```

## 7. 定时轮询协程设计

后端 API 启动时，会启动一个后台 scheduler goroutine。

入口位于 `cmd/api/main.go`：

```go
server := api.NewServer()
server.StartScheduler()
defer server.Close()
```

scheduler 使用 `time.NewTicker` 定时推进状态：

```go
ticker := time.NewTicker(200 * time.Millisecond)
for {
    select {
    case now := <-ticker.C:
        s.safeAdvance(now)
    case <-s.stopScheduler:
        return
    }
}
```

`safeAdvance(now)` 内部调用：

```go
s.controller.AdvanceTo(now)
```

`AdvanceTo(now)` 会检查所有正在处理订单的 bot：

```text
如果 bot.Status == PROCESSING
并且 bot.CompleteAt <= now
    -> 订单进入 COMPLETE
    -> bot 变为 IDLE
    -> bot 尝试继续接下一单
```

使用定时轮询的原因：

- 后端主动推进状态，不依赖前端请求。
- 实现简单稳定，适合 prototype。
- 避免每个订单一个 timer 带来的重置和竞态复杂度。
- 200ms 间隔对 10 秒处理时间来说足够。
- 未来可以在 scheduler 推进状态后接入 WebSocket 或 SSE 推送。

## 8. Scheduler 健康检查设计

Server 维护 scheduler 自身状态：

```go
type Server struct {
    schedulerMu       sync.Mutex
    lastSchedulerTick time.Time
    schedulerInterval time.Duration
    stopScheduler     chan struct{}
    schedulerDone     chan struct{}
    schedulerRunning  bool
}
```

每次 scheduler 成功执行后更新：

```go
lastSchedulerTick = time.Now()
```

`GET /healthz` 会检查：

```text
如果 scheduler 长时间没有 tick
    -> unhealthy
否则
    -> ok
```

正常返回：

```json
{
  "status": "ok",
  "scheduler": "running"
}
```

异常返回：

```json
{
  "status": "unhealthy",
  "scheduler": "stale"
}
```

scheduler 还通过 `recover` 防止单次 panic 导致协程静默退出：

```go
func (s *Server) safeAdvance(now time.Time) {
    defer func() {
        if recovered := recover(); recovered != nil {
            log.Printf("scheduler recovered from panic: %v", recovered)
        }
    }()

    s.controller.AdvanceTo(now)
}
```

`Close()` 会关闭 stop channel 并等待 scheduler goroutine 退出，用于测试和服务优雅关闭。

## 9. API 设计

### 9.1 获取状态

```http
GET /api/state
```

说明：

- 只读取 Controller 快照。
- 不推进业务状态。
- Controller 内部使用读锁。

### 9.2 创建订单

```http
POST /api/orders
Content-Type: application/json

{ "kind": "Normal" }
```

或：

```json
{ "kind": "VIP" }
```

说明：

- Controller 内部使用写锁。
- 创建订单。
- 维护 Pending 优先级。
- 尝试调度空闲 bot。

### 9.3 增加 bot

```http
POST /api/bots
```

说明：

- Controller 内部使用写锁。
- 创建 bot。
- 尝试处理 Pending 订单。

### 9.4 删除最新 bot

```http
DELETE /api/bots/newest
```

说明：

- Controller 内部使用写锁。
- 删除最新创建的 bot。
- 如果该 bot 正在处理订单，将订单放回 Pending。
- 重新维护 VIP/Normal 优先级。

### 9.5 重置系统

```http
POST /api/reset
```

说明：

- Controller 内部使用写锁。
- 清空订单、bot 和事件日志。
- 重新初始化订单号和 bot 编号。

### 9.6 健康检查

```http
GET /healthz
```

说明：

- 检查 API 是否可用。
- 检查 scheduler 是否正常运行。

## 10. 前端设计

前端使用 Vue。

页面展示：

- Pending 订单
- Processing bot
- Complete 订单
- 总订单数
- bot 数量
- busy bot 数量

```http

```

前端轮询只负责刷新页面展示，不负责推进订单状态。订单完成由后端 scheduler 主动推进。

## 12. 设计取舍

### 12.1 为什么用内存存储？

题目明确说明 prototype 不需要数据持久化。内存方案实现简单、方便演示、没有数据库依赖。

缺点是服务重启后状态会丢失，也不支持多实例共享状态。

### 12.2 为什么 Controller 自己加锁？

Controller 是业务状态聚合对象。HTTP API、后台 scheduler、CLI 都可能访问它。把锁放在 Controller 内部，可以让 Controller 自身成为线程安全对象，避免调用方忘记加锁。

### 12.3 为什么用定时轮询协程？

当前订单处理时间固定为 10 秒，使用统一 scheduler 定时推进状态足够简单稳定。

相比 next-deadline timer，固定 ticker 对边界时间、timer reset、状态变化重算的要求更低，更适合这个 take-home prototype。

### 12.4 高并发下怎么办？

当前方案是单进程内存 prototype，使用 `sync.RWMutex` 保证线程安全。

如果扩展到生产系统，可以考虑：

- 数据库存储订单和 bot 状态。
- 使用事务或行锁保证订单流转一致。
- 使用 Redis 或消息队列做调度。
- 使用 WebSocket 或 SSE 推送状态。
- 按餐厅维度拆分 Controller，降低锁竞争。

## 13. 后续可扩展方向
