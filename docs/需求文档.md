# 需求文档

## 1. 项目背景

McDonald's 希望在疫情期间通过自动化 cooking bot 降低人力依赖并提升出餐效率。本项目实现一个订单控制系统原型，用于模拟订单进入、bot 调度、订单完成和 bot 增减的完整流程。

当前实现采用前后端分离：

- 后端：Go，提供 HTTP API，并保留 CLI 演示入口。
- 前端：Vue，提供订单和 bot 管理界面。
- 部署：Docker 容器化部署，宿主机 nginx 提供 HTTPS 域名访问。

## 2. 目标用户

- 普通顾客：提交普通订单，看到订单进入 Pending，并在 bot 处理后进入 Complete。
- VIP 顾客：提交 VIP 订单，订单优先于普通订单处理，但仍保持 VIP 内部先进先出。
- 门店经理：增加或减少 cooking bot 数量，观察订单处理能力变化。
- Cooking bot：一次只能处理一个订单，每个订单处理耗时 10 秒。

## 3. 功能需求

### 3.1 新增普通订单

- 用户点击 `New Normal Order` 后，系统创建一个普通订单。
- 订单号必须唯一且递增。
- 如果没有空闲 bot，订单进入 Pending 区域。
- 如果存在空闲 bot，订单可立即进入 Processing。

### 3.2 新增 VIP 订单

- 用户点击 `New VIP Order` 后，系统创建一个 VIP 订单。
- VIP 订单优先级高于普通订单。
- 新 VIP 订单应排在所有普通订单之前。
- 新 VIP 订单应排在已有 VIP 订单之后。

### 3.3 增加 bot

- 用户点击 `+ Bot` 后，系统创建一个新的 cooking bot。
- 新 bot 创建后应立即尝试处理 Pending 中的最高优先级订单。
- 如果 Pending 为空，bot 状态为 `IDLE`。

### 3.4 减少 bot

- 用户点击 `- Bot` 后，系统删除最新创建的 bot。
- 如果该 bot 处于 `IDLE`，直接删除。
- 如果该 bot 正在处理订单，应停止处理，并将订单放回 Pending。
- 放回 Pending 后仍需保持 VIP/普通订单优先级规则。

### 3.5 订单处理

- 每个 bot 同一时间只能处理一个订单。
- 每个订单从被 bot 拾取开始，10 秒后进入 Complete。
- bot 完成一个订单后，应自动继续处理下一个 Pending 订单。
- 如果没有 Pending 订单，bot 进入 `IDLE`。

### 3.6 状态展示

前端页面需要展示：

- Pending 订单列表
- Processing bot 和正在处理的订单
- Complete 订单列表
- 订单总数、bot 总数、忙碌 bot、空闲 bot、完成订单数
- 系统活动日志

### 3.7 CLI 演示

后端需要保留 CLI 能力，以满足原技术测试对后端 CLI 的要求：

- `scripts/test.sh` 执行单元测试。
- `scripts/build.sh` 编译 CLI 和 API。
- `scripts/run.sh` 运行 CLI demo 并输出到 `scripts/result.txt`。
- `scripts/result.txt` 中事件日志需包含 `HH:MM:SS` 格式时间戳。

## 4. 非功能需求

- 无需数据库持久化，所有状态保存在后端内存中。
- 服务重启后订单和 bot 状态可清空。
- 前端不得自行实现调度规则，业务规则由 Go 后端统一维护。
- 支持 Docker 本地部署。
- 生产访问通过 nginx 和 HTTPS 暴露。

## 5. 验收标准

- 普通订单可以创建并展示。
- VIP 订单在 Pending 中优先于普通订单。
- 订单号递增且不重复。
- 增加 bot 后可立即处理 Pending 订单。
- bot 处理订单 10 秒后订单进入 Complete。
- bot 完成订单后可自动处理下一单。
- 删除正在处理订单的 bot 后，订单回到 Pending。
- 页面刷新或后台轮询时，操作按钮不应出现明显闪烁。
- VIP 订单号在 Pending 和 Complete 区域可正常显示。
- Docker 容器启动后，前端可通过配置域名访问。
